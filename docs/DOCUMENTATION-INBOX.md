# Документация: share-inbox (для админа)

Массовая заливка больших деревьев (100+ МБ в день) **не через браузер**, а копированием в папку на диске сервера. API сам создаёт папки/файлы в разделе документации и пишет записи в БД.

Обычная кнопка «Загрузить» в UI по-прежнему ограничена ~20 МБ — inbox для тяжёлых объёмов.

## Где лежит inbox

Корень = `ATTACHMENTS_HOST_PATH` из `.env` (тот же bind-mount, что и вложения заявок).

```
{ATTACHMENTS_HOST_PATH}/docs-inbox/
  README.txt
  {логин_подразделения}/     ← основной каталог
  {guid_N}/                  ← запасной (Id пользователя без дефисов)
```

Примеры:

| На хосте | В контейнере API |
|---|---|
| `./data/attachments/docs-inbox/otdel_a/` | `/data/attachments/docs-inbox/otdel_a/` |
| `/mnt/data2/crown-attachments/docs-inbox/otdel_a/` | то же внутри `/data/attachments/...` |

Папки подразделений API создаёт сам при старте/синке (роль **Подразделение**, `DocumentationEnabled`).

Имя папки = логин пользователя (`UserName`), символы `/ \ :` и пр. → `_`. Если логин пустой — только `{guid:N}`.

Путь для конкретного раздела также виден в UI документации (под кнопкой «Импорт из inbox»).

## Как залить

1. Откройте share / SMB / scp на каталог `docs-inbox/{логин}/`.
2. Скопируйте файлы и подпапки **как должно быть в разделе** (структура папок сохраняется).
3. Дождитесь автосинка (**~5 минут**) или нажмите **Импорт из inbox** в UI раздела (админ / диспетчер / само подразделение).
4. Админ может дернуть всё сразу: `POST /api/documentation/sync-inbox`.

После успеха исходники переезжают в:

```
docs-inbox/{логин}/.processed/{yyyyMMdd_HHmmss}/...
```

Ошибки (битый файл, превышен лимит и т.п.):

```
docs-inbox/{логин}/.errors/{yyyyMMdd_HHmmss}/...
```

Каталоги `.processed`, `.errors`, `.tmp` и скрытые `.*` **не импортируются**.

## Лимиты

| Что | Лимит |
|---|---|
| Файл через UI | `Attachments:MaxFileBytes` (по умолчанию 20 МБ) |
| Файл из inbox | `Attachments:MaxInboxFileBytes` (по умолчанию **512 МБ**) |

Переопределение в `docker-compose` / env:

```yaml
Attachments__MaxInboxFileBytes: "1073741824"   # 1 ГБ
```

## Идемпотентность

У файла в БД есть `InboxSourceKey` = относительный путь внутри inbox (например `Отчёты/2026/свод.pdf`).

- тот же путь + тот же размер → пропуск, файл всё равно уезжает в `.processed`;
- тот же путь + другой размер → файл в разделе **обновляется**;
- повторно положили тот же путь завтра → снова импорт/обновление.

Удаление в UI (корзина) не мешает заново залить тот же ключ.

## Права на диск (Windows / Linux)

- Процесс API (пользователь контейнера) должен **читать и перемещать** файлы в `docs-inbox`.
- Share лучше отдать группе, которая копирует дампы; API — полные права на `docs-inbox`.
- Не кладите inbox на read-only volume.

### SMB (эскиз)

На хосте расшарьте только `…/docs-inbox` (или подпапку подразделения), не весь `attachments` с заявками.

## Типовой ежедневный сценарий

1. Ночной/дневной job копирует дерево в `docs-inbox/otdel_a/Архив/…`.
2. Через ≤5 мин (или по кнопке) файлы появляются в разделе «otdel_a» в Crown.
3. Раз в неделю чистите старые `.processed` / `.errors` вручную (место на диске).

## Диагностика

```bash
# логи синка
docker logs crown_api 2>&1 | findstr /i "inbox"

# что лежит на диске
dir data\attachments\docs-inbox
# или
ls -la /mnt/data2/crown-attachments/docs-inbox
```

Миграция БД `DocumentationInboxSourceKey` накатывается при старте API автоматически.

## Чего inbox не делает

- не распаковывает zip (кладите уже развёрнутое дерево или отдельные файлы);
- не меняет права ролей / видимость разделов;
- не трогает файлы, загруженные только через UI (у них нет `InboxSourceKey`).
