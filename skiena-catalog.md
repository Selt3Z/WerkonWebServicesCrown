# Каталог Скиена (Steven S. Skiena)

Рекомендации «когда да / когда нет» по 3-му изд. «Алгоритмы. Руководство по разработке» (БХВ, 2022). Источники: книга (часть I + «Обсуждение» в каталоге части II) + доработка из `skiena_recommendations.docx` (Grok).

Формат: **Да** = типичный рабочий кейс; **Нет** = когда лучше другое (после `→`); **Пример** — рабочий сценарий; **Книга** — раздел.

Пометки:
- `(пр.)` — в книге прямо нет, общая инженерная практика.
- Номера разделов из Grok-дока выборочно не перепроверены по PDF — при цитировании сверяй.

## Три главных совета Скиены

1. Сначала определи, какая это задача (почти всегда переодетая известная), найди в каталоге (гл. 15–21), бери готовую библиотеку (гл. 13, 14, 22).
2. Не знаешь, что делать — отсортируй: дубли, ближайшие, медиана, пересечения решаются одним проходом (4.1, 17.1).
3. Задача NP-трудная — не тупик: мало данных → перебор с отсечениями; средне → ILP/SAT-солвер; много → эвристики (гл. 11–12).

Ориентиры порядка величин: перебор подмножеств n≈20 → 10⁶, n=30 → 10⁹; перестановки n≈10–12 ок, n=15 → >10¹²; обходы графа (BFS/DFS) — миллионы вершин за секунды.

## Предел n по классу сложности (табл. 2.1, 1 операция = 1 нс)

| Класс | Практический предел | Опорные точки из книги |
|-------|---------------------|------------------------|
| lg n | любой n | 10⁹ → 0,03 мкс |
| n | ~10⁹ | 10⁹ → 1 с |
| n lg n | ~10⁹ | 10⁹ → 30 с |
| n² | ~10⁴ комфортно, >10⁶ бесполезно | 10⁶ → 16,7 мин; 10⁸ → 116 дней |
| 2ⁿ | n ≲ 40 | n=40 → 18 мин; n=50 → 13 дней |
| n! | n ≲ 12–15 | n=10 → 3,6 мс; n=20 → 77 лет |

Правило агента: оцени n и класс **до** выбора алгоритма; если класс не влезает — меняй алгоритм/модель, а не железо.

## Чек-лист выбора (гл. 13, «список вопросов разработчика»)

1. **Понимание:** что на входе, что точно на выходе; реши вручную маленький пример; нужен ли оптимум или «близко к лучшему»; типичный n (10 / 10³ / 10⁶ / больше); бюджет времени (секунда / минута / час / день); сколько времени на реализацию (день → только простое).
2. **Простое решение:** работает ли полный перебор и почему он корректен; есть ли простое правило (наибольший / наименьший / случайный первым) — на каких входах оно хорошо, на каких плохо; если плохой вход не находится — можно ли доказать корректность.
3. **Каталог:** есть ли задача в каталоге (гл. 15–21), есть ли готовая реализация; искал ли по всем ключевым словам/рисункам.
4. **Частные случаи:** станет ли проще, если игнорировать часть параметров или задать им 0/1; не частный ли это случай общей задачи каталога.
5. **Парадигма:** можно ли отсортировать и станет ли проще; можно ли делить пополам (D&C, бинарный поиск); есть ли естественный порядок слева направо (строка, перестановка, листья дерева) → DP; повторяются ли min/max/lookup → куча/хеш; поможет ли случайная выборка или отжиг; формулируется ли как LP/ILP; похожа ли на SAT/TSP/другую NP-полную.
6. **Записывай ответы «нет, потому что…»** — ошибочное «нет» без причины часто скрывает упущенный вариант.
7. Стратегия раньше тактики: сначала «это граф?», потом «список или матрица смежности?».

## 1. Базовые методы и парадигмы проектирования

### Жадные алгоритмы
- **Да:** доказано, что локальный выбор оптимален (MST Прим/Крускал, Дейкстра, максимум непересекающихся интервалов по раннему окончанию); быстрый «достаточно хороший» ответ на трудной задаче (упаковка «крупное первым», покрытие множества); данных очень много — обычно сортировка + один проход.
- **Нет:** правило придумано и не проверено — Скиена показывает контрпримеры на 4–5 элементах («Жадные кинозвёзды») → сначала ищи контрпример, потом DP/перебор; точная сумма/вес («рюкзак», subset sum) → DP; нужен оптимум в трудной задаче (маршрут через 50 точек) → жадный лишь как старт для улучшения.
- **Пример:** одна переговорка, 40 заявок → сортировка по времени окончания. Плохо: «курьер в ближайшую точку» — маршрут на 20–50 % длиннее.
- **Где жадность доказуемо оптимальна (из каталога):** дробный рюкзак (по цене за кг, 16.10); рюкзак с одинаковой ценой предметов → брать по возрастанию размера; с одинаковым размером → по убыванию цены; MST; интервалы по раннему окончанию.
- **Где жадность даёт гарантированное приближение:** покрытие множества — ≤ ln n от оптимума (на практике заметно лучше); доминирующее множество — то же; вершинное покрытие «вершина макс. степени» — до lg n хуже (берите 2-approx через паросочетание, 19.3).
- **Где жадность может быть сколь угодно плохой:** 0/1-рюкзак по цене за кг — но годится для отсечения «дешёвых и тяжёлых» предметов перед перебором (16.10).
- **Книга:** 1.1–1.3.3, 8.1, 12.5, 16.10, 19.3, 21.1.

### Рекурсия и индукция
- **Да:** вложенные данные (каталоги, JSON, комментарии, оргструктура); «то же, но поменьше»; нужно доказать корректность («база + шаг»); умеренная глубина (сотни–тысячи).
- **Нет:** подзадачи пересчитываются (Фибоначчи в лоб: n=50 — минуты) → кэш/DP; глубина огромная (список на 10⁶ узлов) → цикл + явный стек (пр.); не проверены базовые случаи (пусто, 1 элемент) → тесты.
- **Книга:** 1.3.4, 1.4.2, 5.3–5.4.

### Инкрементные алгоритмы
- **Да:** данные приходят по одному, ответ нужен после каждого; добавление дёшево (вставка в маленький отсортированный список, счётчики); n мало или почти упорядочено; простая доказуемость.
- **Нет:** каждое добавление пересматривает всё (сдвиг массива 10⁶) → собрать целиком и обработать раз (сортировка, D&C) или структура (дерево/куча); вход может быть «неудачным» (отсортирован по убыванию) → перемешать вход (пр.).
- **Пример:** топ-10 последних дорогих заказов — вставка в список из 10.
- **Книга:** 1.3.4, 2.5.2, 4.3.5.

### Метод «разделяй и властвуй»
- **Да:** независимые подзадачи, дешёвая склейка (merge sort, бинарный поиск, ближайшая пара, Карацуба/FFT, max subarray); n от десятков тысяч, где O(n²) мало; нужен параллелизм; данные не влезают в память (внешняя сортировка).
- **Нет:** подзадачи пересекаются → DP; склейка стоит как всё решение; куски слишком мелкие (~десяток элементов) → переключаться на insertion sort.
- **Пример:** лог 50 ГБ при 8 ГБ RAM — куски, сортировка, слияние.
- **Книга:** гл. 5 (5.1–5.9), 4.5.

### Рандомизированные алгоритмы
- **Да:** простой алгоритм тормозит на «плохих» данных (отсортированный вход в quicksort); быстрая вероятностная проверка (простота, равенство файлов, Карп–Рабин); выборка/оценки/случайный поиск для трудных задач; защита от adversarial-ввода (hash flooding).
- **Нет:** ошибка недопустима и нечем перепроверить (финрасчёты) → детерминированный или повтор с проверкой; нужна воспроизводимость → фиксируй seed, логируй; плохой ГСЧ (самописный, «время в мс») → стандартный, для безопасности — криптографический.
- **Пример:** A/B-группы — случайно, не «по чётности ID».
- **Генератор случайных чисел (16.7):**
  - для игр — seed из младших битов часов; для моделирования — детерминированный ГПСЧ, seed хранить в файле между запусками (для отладки подставлять фиксированный);
  - встроенный генератор — ок, если точность моделирования не критична; иначе проверять статистическими тестами (набор NIST), «на глаз» случайность не оценить;
  - линейный конгруэнтный генератор с 32-битным словом исчерпывает период 2³² за минуты → нужны генераторы с длинным периодом;
  - неравномерное распределение → метод выборки с отклонением (бросаем точку в охватывающее окно, отбрасываем промахи); медленно, если область мала относительно окна;
  - ловушка: точка в круге через «случайный угол + случайный радиус r» неравномерна (половина точек в радиусе r/2 вместо четверти);
  - Монте-Карло: не гнать один длинный прогон, а 10–100 прогонов с разными seed и смотреть разброс результатов.
- **Ловушки равномерности (12.6.1, 17.4):** случайная неупорядоченная пара через `i=rand(1,n-1); j=rand(i+1,n)` неравномерна (пара (n−1,n) в n−1 раз чаще (1,2)) → брать два независимых числа, упорядочить, при i=j повторить. Проверка shuffle: 10 000 случайных перестановок из 4 элементов — все 24 должны встречаться примерно поровну.
- **Книга:** 4.6.2, гл. 6, 8.6, 12.6.1, 16.7, 17.4.

### Параллельные алгоритмы (параллелизм на уровне данных)
- **Да:** куски действительно независимы («чрезвычайно параллельные»: тысячи файлов, прогон параметров); уже выбран лучший последовательный алгоритм; каждая часть ≫ накладных (секунды+).
- **Нет:** медленно из-за алгоритма — 24 ядра дают ≤24×, правильный алгоритм часто ×1000 → профилировщик и алгоритм сначала; частые обмены/общая запись (гонки, блокировки); задача на секунды.
- **Пример:** пережать 10 000 фото в пуле процессов. Плохо: баланс по цепочке транзакций.
- **Книга:** 5.7–5.8.

### Перебор с возвратом (Backtracking)
- **Да:** перечислить все варианты; точный ответ на трудной задаче при малом n (обычно 15–25, с хорошим pruning до 50–100); много ограничений быстро режут ветви (судоку, конфигураторы); эталон для проверки эвристики.
- **Нет:** n десятки–сотни и ограничения слабые → DP (если есть порядок), ILP/SAT, эвристики гл. 12; есть быстрый известный алгоритм (путь, паросочетание, сортировка).
- **Пример:** подарочный набор из 12 товаров ровно на 5000 ₽ — доли секунды; из 200 — нет.
- **Приёмы реализации:**
  - стоимость нового кандидата считать инкрементно от предыдущего (в переборе TSP соседние перестановки отличаются 4 рёбрами — не пересчитывать весь маршрут, 17.4);
  - перестановки мультимножества (есть повторы) генерировать в лексикографическом порядке перебором с возвратом — для {1,1,2,2,2} это 10 вариантов вместо 120;
  - перед точным перебором проверь дешёвые необходимые условия (для гамильтонова цикла — двусвязность: есть шарнир → цикла нет, 19.5).
- **Книга:** 9.1–9.4, 17.4–17.5, 19.5.

### Отсечение вариантов поиска (Pruning)
- **Да:** всегда вместе с backtracking; частичное решение нарушает ограничение (бюджет, конфликт); ветка точно хуже найденного рекорда (branch-and-bound); начинать с самой «тесной» переменной (судоку — клетка с минимумом кандидатов).
- **Нет:** отсечение «скорее всего хуже» без гарантии, а нужен точный ответ (молча потеряешь оптимум) → строгие правила или честная эвристика; оценки грубые и ничего не режут → ILP-солвер/эвристики.
- **Книга:** 9.3, 9.4, 9.6.

### Динамическое программирование (кэширование / мемоизация, восстановление пути)
- **Да:** рекурсия пересчитывает одно и то же; объекты упорядочены (строки, последовательности, ряды, позиции, деревья); подзадач тысячи–миллионы; нужен не только «ответ», но и путь (edit distance → правки, рюкзак → предметы).
- **Нет:** объекты не упорядочены, состояние = любое подмножество (самый длинный простой путь, TSP на 30–40) → эвристики/перебор с отсечением; оптимум целого не складывается из оптимумов частей (10.9.1) — ответ будет неверным; таблица не влезает (2 строки по 10⁵ символов = 10¹⁰ клеток) → храни последние строки, для пути — алгоритм Хиршберга.
- **Пример:** diff двух версий договора, «вы имели в виду…», разбиение очереди задач между 3 исполнителями.
- **Связь с графами (18.4):** большинство DP-задач — кратчайший (или, с max, самый длинный) путь в DAG: топосорт + проход слева направо, линейное время. Если задачу удаётся нарисовать как DAG состояний — решение готово.
- **Оптимальное BST (17.2):** если частоты запросов к ключам известны заранее и статичны — DP строит дерево поиска с минимальной ожидаемой стоимостью (каждый корень делит ключи на два поддиапазона).
- **Книга:** гл. 10 (10.1–10.9), 17.2, 18.4.

### Сведение задач (Reductions) и задачи разрешимости
- **Да:** задача похожа на известную — переформулируй под готовый алгоритм (дубли → сортировка + соседи; ближайшая пара 1D → сортировка); понять, стоит ли искать точное решение (к твоей сводится известная NP-трудная → не стоит); перевод в язык готового солвера (SAT, ILP, поток).
- **Нет:** направление сведения перепутано: чтобы показать «моя трудная», нужно свести **известную трудную к моей**, а не наоборот; задача решается быстрым специальным алгоритмом, а её суют в общий солвер → сначала каталог.
- **Пример:** раскраска графа для дежурств на 300 человек → трудная, нужна эвристика.
- **Как доказывать трудность (17.10, гл. 11):** сначала поищи задачу в списке Гэри–Джонсона [GJ79]; если нет — своди к своей одну из базовых: 3-SAT, вершинное покрытие, независимое множество, разбиение целых чисел, клика, гамильтонов цикл.
- **Полезные сведения «вниз» (к лёгкому):** вершинное покрытие ↔ независимое множество (дополнение множества вершин) ↔ клика в дополнении графа; гамильтонов цикл → TSP (рёбра = 1, неребра = 2); покрытие множества с подмножествами по 2 элемента → паросочетание; много задач на графах → max-flow; DP → путь в DAG.
- **Книга:** 11.1–11.6, 11.9, 17.10, 19.2, 19.5, 21.1.

### Целочисленное программирование
- **Да:** трудная дискретная задача со множеством бизнес-ограничений (смены, раскрой, распределение заказов); нужен оптимум или оценка отрыва от него; размер средний (сотни–тысячи переменных), есть минуты; требования меняются — проще править модель.
- **Нет:** переменные дробные (деньги, литры) → LP (16.6) быстрее; есть специальный алгоритм (путь, поток, паросочетание); огромный размер или миллисекунды (11.5.2) → эвристики.
- **Пример:** график 40 операторов колл-центра. Бюджет рекламы по каналам в рублях → LP.
- **LP/ILP на практике (16.6):**
  - свой симплекс не писать; Скиена: платные солверы LP превосходят бесплатные во всех отношениях; методы внутренней точки во многих задачах быстрее симплекса;
  - ограничений больше, чем переменных → решать двойственную задачу (или двойственным симплексом); переменных больше → прямую;
  - время ILP непредсказуемо (зависит от конкретного экземпляра) — закладывай лимит времени и берите лучшее найденное;
  - нелинейная цель: сначала попробовать переформулировать (МНК имеет быстрые методы), общее квадратичное программирование NP-полно → спецсолверы или общая оптимизация (16.5);
  - солвер требует стандартную форму (min, x ≥ 0, равенства): max → min сменой знака, неравенства → slack-переменные, либо язык моделирования (AMPL);
  - кратчайший путь, двудольное паросочетание, поток — частные случаи LP, но специализированные алгоритмы намного быстрее; TSP, покрытие множества, рюкзак — через ILP.
- **Книга:** 11.5.2, 16.5, 16.6.

### Эвристический поиск: случайная выборка, локальный поиск, имитация отжига
Общие компоненты: представление кандидата решения (как в backtracking) + функция стоимости. Эксперимент Скиены на TSP со 150 узлами (оптимум 6828): 10⁸ случайных выборок → 43 251 (в 8 раз хуже); локальный поиск → 15 715 (в 2,3 раза хуже, хуже даже MST-эвристики); имитация отжига → близко к оптимуму.
- **Случайная выборка — Да:** хороших решений много («травинка в стоге, а не иголка»); пространство неоднородно, нет признаков приближения (поиск больших простых — каждое ~ln n-е число простое). **Нет:** хороших решений мало (TSP, большинство задач оптимизации).
- **Локальный поиск / hill climbing — Да:** пространство гладкое/выпуклое с одной вершиной (бинарный поиск, симплекс — частные случаи); оценка изменения намного дешевле полной оценки (обмен 2 вершин в TSP — O(1) вместо Θ(n)). **Нет:** много локальных оптимумов — застревает («крыша отеля, а не вершина горы»); рестарты с других точек помогают слабо.
- **Имитация отжига — Да:** по Скиене самый надёжный практический метод для трудных комбинаторных задач. Параметры для старта: T₀ = 1; T_k = α·T_{k−1}, α ∈ [0,8; 0,99] (экспоненциальное охлаждение); ~1000 итераций на температуру (держать дольше, пока есть прогресс); «хороший» переход принимать всегда, «плохой» — если e^((C_old − C_new)/(k·T)) > r, r ∈ [0,1), k подобрать так, чтобы при T₀ принимались почти все переходы; стоп — нет улучшений за последние итерации. График охлаждения подбирается экспериментом.
- **Механизмы перехода:** обмен двух элементов; вставка/удаление одного элемента; замена двух рёбер маршрута (лучше обмена вершин).
- **Генетические алгоритмы — Нет (по Скиене):** на практических задачах комбинаторной оптимизации работают хуже отжига: моделирование мутациями/скрещиванием на битовых строках неестественно, не использует структуры данных задачи и очень медленно.
- **Аппроксимирующие алгоритмы (12.1–12.5):** дают гарантию близости к оптимуму — вершинное покрытие ≤ 2×, метрический TSP через MST ≤ 2×, покрытие множества ≤ ln n. Брать, когда нужна гарантия, а не «обычно хорошо».
- **Книга:** 12.1–12.6, 12.9.

## 2. Структуры данных

Неправильная структура — самая частая причина «тормозит». Граф хранить списком соседей; матрица смежности — только малые/очень плотные графы (7.2, 15.4).

### Представление графа (15.4)
- **Списки смежности — по умолчанию:** большинство алгоритмов (всё на DFS/BFS), разреженные графы; планарные графы всегда разреженные (≤ 3n − 6 рёбер).
- **Матрица смежности — Да:** граф малый или очень плотный (1000 вершин = 10⁶ ячеек — нормально); APSP (Флойд); частые проверки «есть ли ребро (i,j)». Если нужны **только** такие проверки — хеш-таблица рёбер.
- **Атрибуты** (вес, метка, цвет) меняются чаще топологии — хранить полями в записях рёбер/вершин списка.
- **Статический граф** (без вставок/удалений) — списки заменить упакованными массивами ID вершин: минус указатели, ~вдвое меньше памяти.
- **Постоянный онлайн-граф** (соцсеть, CRM-связи) — не in-memory список, а графовая БД (Neo4j).
- **Гиперграф** (ребро связывает много вершин: участники комитетов) — матрица инцидентности n×m или двудольная структура инцидентности (для разреженных).
- **Огромный граф:** битовая матрица, упаковка, иерархическая декомпозиция (естественная — город/район/область — лучше алгоритмического разбиения).
- Конвертация матрица ↔ список линейна; если не ясно, что выбрать, и память есть — держать обе.
- Свой универсальный тип графа не писать — сначала библиотека (LEDA, Boost, NetworkX).

### Массивы
- **Да:** доступ по номеру; чтение/проход (кэш-friendly); известный размер или добавление в конец (list/ArrayList/vector); статический справочник — отсортированный массив + бинарный поиск; n≲50–100 в роли словаря.
- **Нет:** частые вставки/удаления в середине на больших n (на 10⁶ в среднем сдвиг 5·10⁵) → дерево/список/deque; частый поиск по значению в неотсортированном → хеш.
- **Пример:** очередь задач в массиве с забором из начала — плохо, нужен deque.
- **Книга:** 3.1.1, 3.1.3.

### Связные списки (поиск, вставка, удаление)
- **Да:** вставка/удаление там, где уже стоишь (есть ссылка на соседа); неизвестный и сильно меняющийся размер; внутренности стека/очереди/цепочек хеша/LRU (список + словарь); самоорганизующийся список (найденный → в начало) при n≲50–100 с локальностью обращений.
- **Нет:** поиск по значению/номеру на сотнях+ (после 50–100 элементов линейный поиск «сводит на нет преимущества») → хеш/дерево; нужен быстрый обход больших объёмов (элементы разбросаны по памяти) → массив.
- **Книга:** 3.1.2–3.1.3, 15.1.

### Стеки и очереди
- **Да:** стек — вернуться назад (undo, скобки, DFS, разбор выражений); очередь — по порядку поступления (задачи, сообщения, BFS, буфер); нужны только «положить»/«взять».
- **Нет:** нужен «самый важный/срочный» → очередь с приоритетами; нужно удалять из середины («отменить задачу №X») → словарь + пометка «отменено» или дерево.
- **Книга:** 3.2.

### Словари
Не структура, а интерфейс «ключ → значение»; Скиена: важнее не взять неподходящую структуру, чем найти лучшую; **изолируй интерфейс от реализации** — легко пробовать варианты. Выбирай по вопросам: сколько элементов; соотношение insert/delete/search; равномерны ли обращения (асимметрия → splay/самоорганизующиеся); критична ли каждая операция или суммарно.
- **Да:** точный ключ → хеш (dict/HashMap); нужен порядок/диапазоны/«следующий» → сбалансированное дерево (TreeMap, std::map, SortedDict); данные почти не меняются → отсортированный массив + бинарный поиск; n≲50 — что угодно; полудинамический (только вставки) — проще полностью динамического.
- **Нет:** тысячи записей в неупорядоченном списке с перебором → хеш; поиск по префиксу/подстроке/похожим → trie/суффиксные структуры (15.3), нечёткий поиск (21.4).
- **Пример:** кэш ID → профиль (хеш); котировки «цена до 14:03» (дерево).
- **Подробности (15.1, 17.2):**
  - упорядоченный **список** не стоит усилий (бинарный поиск по нему невозможен), разве что ради отсечения дубликатов; упорядоченный **массив** — только при редких вставках/удалениях;
  - самоорганизующийся список (move-to-front) выигрывает при неравномерных обращениях и временной локальности (закон Ципфа — правило, а не исключение); после ~100 ключей → бинарный поиск/дерево;
  - списки с пропусками (skip list) — альтернатива сбалансированному дереву: O(lg n) в ожидании, проще реализовать и анализировать;
  - данные не влезают в RAM → B-деревья (несколько уровней BST в одном узле = меньше обращений к диску); следить за свопом — даже небольшие данные могут неожиданно тормозить из-за подкачки.
- **Книга:** 3.3, 15.1, 17.2.

### Двоичные деревья поиска (поиск, обход, вставка, удаление, min/max)
- **Да:** данные меняются и нужен порядок (min/max/следующий/диапазоны); ключи приходят в случайном порядке (дерево само ок, 3.4.2); учёба/понимание TreeMap и индексов БД.
- **Нет:** ключи отсортированы/почти (ID, даты, номера заказов) — дерево вытягивается в «палку», O(n) на операцию → сбалансированное из библиотеки; порядок не нужен → хеш; хочется самописное для прод → готовое из stdlib.
- **Книга:** 3.4.1–3.4.2.

### Сбалансированные деревья поиска
- **Да:** ordered map/set: поиск/вставка/удаление + min/max/prev/next/диапазон; гарантия на любых и adversarial-данных; данные на диске → B-деревья.
- **Нет:** писать самому (ловушки балансировки) → TreeMap/std::map/sortedcontainers; только точный ключ → хеш; статичные данные → отсортированный массив.
- **Нюанс Скиены:** AVL и 2-3 считаются устаревшими → красно-чёрные; splay — когда к одним ключам обращаются часто (отличная амортизированная производительность при меняющихся частотах). Тип дерева важен меньше, чем качество реализации: «лучшее — то, для которого у вас лучшая реализация».
- **Пример:** биржевой стакан; таблица броней «ближайшая после 18:00».
- **Книга:** 3.4.3, 15.1.

### Очереди с приоритетами и пирамиды (кучи / Heaps)
- **Да:** чередуются insert и extract-min (планировщик, таймеры, симуляция, Дейкстра, Прим, A*, слияние отсортированных файлов); топ-K из потока (куча размера K); ключи — малые целые (1..10) → массив списков по приоритету (корзины); известна верхняя граница → binary heap.
- **Нет:** нужен поиск/удаление произвольного элемента → сбалансированное дерево или куча с пометкой «удалено» (пр.); вставок после старта нет → один раз отсортировать (как в Крускале); фибоначчиева куча «ради скорости» → binary heap из stdlib.
- **Вопросы перед выбором (15.2):** нужны ли поиск/удаление произвольного ключа или только top; известен ли максимальный размер (binary heap на массиве; иначе динамический массив); нужно ли менять приоритет уже стоящих элементов (decrease-key → нужен доступ по ключу).
- **Про продвинутые кучи (15.2, примечания):** фибоначчиевы/парные кучи ускоряют decrease-key (Дейкстра/Прим на больших графах), но фибоначчиевы трудно реализовать и у них большие константы; эксперименты: простые binary heap конкурентоспособны в большинстве приложений, парные кучи быстрее фибоначчиевых. Если всё же нужно — pairing heap.
- **Bounded-height очередь (корзины по ключу 1..n + указатель top):** insert и find-min за O(1); идеальна для вершин графа по степени (жадные эвристики покрытия/клики), применяется реже, чем заслуживает.
- **Пример:** тикеты VIP/истекающий SLA первыми.
- **Книга:** 3.5, 4.3, 15.2.

### Хеш-таблицы и хеширование (коллизии, идеальное, каноникализация)
Коллизии: цепочки или открытая адресация (удаление при ней — боль). Идеальное хеширование — фиксированный набор ключей. Каноникализация — привести «равное по смыслу» к одному виду (отсортировать буквы → анаграммы; email lower; телефон = цифры).
- **Да:** выбор по умолчанию для поиска/добавления/удаления по точному ключу; дубли и пересечения (set); сравнение «по смыслу» после каноникализации; фиксированный набор ключей (ключевые слова, коды стран) → идеальное хеширование.
- **Нет:** нужен порядок (диапазоны, min, «следующий») → дерево/отсортированный массив; ключи выбирает злоумышленник при предсказуемом хеше (hash flooding) → рандомизированный хеш с секретным seed; короткий хеш как «уникальный ID» — парадокс дней рождения: 32-бит ≈ коллизия уже при ~80 000 записей → ≥128 бит + проверка значения.
- **Пример:** сверка клиентов CRM и рассылки: lower(email) → set.
- **Настройка своей хеш-таблицы (15.1):**
  - цепочки: число корзин m ≈ ожидаемому максимуму элементов; открытая адресация: m больше максимума минимум на 30–50 % (при высоком коэффициенте заполнения производительность падает);
  - m — простое число: компенсирует слабости неудачной хеш-функции;
  - строки: полиномиальный хеш по правилу Горнера; вариант Карпа–Рабина пересчитывает хеш скользящего окна из k символов за O(1);
  - проверяй статистику заполнения корзин — первая выбранная хеш-функция обычно не лучшая, плохая хеш-функция заметно снижает производительность.
- **Книга:** 3.7, 6.3, 6.5, 6.7, 15.1.

### Фильтры Блума
- **Да:** огромное множество (10⁸ URL/email/ключей), память дорога; быстрый фильтр перед дорогой проверкой («нет» → к базе не идём); ложное «да» допустимо (его отсеет вторая проверка), ложное «нет» — нельзя.
- **Нет:** нужна точность без второй проверки → set/хеш; нужны удаления (классический не умеет) → хеш или counting Bloom (пр.); данные влезают в обычный set → set; размер «на глаз» — при переполнении почти все «да» → считать под n и допустимый FP-rate.
- **Пример:** краулер: «видели URL?»; проверка пароля по базе утечек на клиенте; проверка правописания (пропуск редкого опечатанного слова — не трагедия, пример Скиены).
- **Механика (15.5):** k независимых хеш-функций, при вставке ставим k битов; элемент «возможно есть», только если все k битов = 1. Больше функций и больше битов → меньше ошибок. Лучше всего для статичных множеств.
- **Книга:** 6.4, 15.5.

### Множества и битовые векторы (15.5)
- **Битовый вектор — Да:** фиксированное универсальное множество, плотные подмножества; вставка/удаление — переключить бит; объединение/пересечение — побитовые OR/AND. **Нет:** разреженные подмножества (перечисление элементов O(n) даже для пустого).
- **Отсортированный контейнер/словарь — Да:** разреженные подмножества, нет фиксированного универсума; объединение/пересечение — слиянием за линейное время.
- **Разбиение на непересекающиеся группы** («в каком множестве элемент?», «в одном ли?») → DSU; массив «элемент → имя группы» даёт O(1) запрос, но слияние O(n).
- **Мультимножество** — поле-счётчик у элемента.
- Подмножества ровно по 2 элемента — это рёбра графа: проверь, не сводится ли задача к компонентам/путям.
- Пример объёма: битовый вектор нечётных чисел до 10⁶ — < 64 КБ (16.8).
- **Книга:** 15.5, 16.8.

### Trie, суффиксные деревья и массивы (15.3)
- **Trie — Да:** множество строк, проверка вхождения/префикса за |q| сравнений независимо от числа строк; простая вставка. **Нет:** память критична (trie прожорлив).
- **Суффиксное дерево — Да:** много запросов к одному тексту — все вхождения q за O(|q| + k); наибольшая общая подстрока набора строк (одно дерево по всем строкам); самый длинный палиндром (дерево по S и обращённой S). Часто сводит O(n²) обработку строк к линейной. **Нет:** писать свой линейный алгоритм построения → готовая реализация.
- **Суффиксный массив — предпочтительнее дерева:** почти те же возможности, проще реализовать, ~в 4 раза меньше памяти, поиск обычно не медленнее (бинарный поиск за lg n + |q| сравнений символов с массивом LCP).
- **Книга:** 3.9, 15.3, 21.8.

### Kd-деревья и пространственные индексы (15.6)
- **Да:** 2–20 измерений: поиск ячейки точки, ближайший сосед (проверить и соседние ячейки в радиусе найденного расстояния), поиск в прямоугольной области, поиск по частичному ключу (известны не все координаты).
- **Нет:** > ~20 измерений — объём шара падает экспоненциально, число проверяемых ячеек и соседей (до 2^k) взрывается → шаровые деревья (ball tree), снижение размерности, отказ от наименее важных измерений.
- **Варианты:** циклическое чередование измерений; разрез по наибольшему измерению (ячейки ближе к квадрату); quad/oct-деревья (изображения, области одного цвета); RP-деревья (случайные направления — лучше, когда данные лежат на низкоразмерной структуре); BSP (секущие плоскости общего положения).
- **Книга:** 15.6, 20.5–20.7.

### Метод минимальных хеш-кодов (MinHash)
- **Да:** почти-дубликаты документов/объявлений/профилей среди миллионов; сходство = доля общих элементов (Jaccard: слова, теги, покупки); сравнить «всё со всем» долго, приближённое «≈80 %» устраивает.
- **Нет:** документов сотни–тысячи и нужна точность → пересечение через set; важен порядок/опечатки («Иванов Иван» vs «Иванов Ивн») → edit distance; точные дубли → хеш содержимого.
- **Книга:** 6.6.

### DSU (Disjoint Set Union / поиск-объединение)
- **Да:** связи только добавляются, нужно «в одной ли группе?»; Крускал; склейка дублей по цепочке признаков (телефон → email → карта); миллионы объединений: union by size + path compression ≈ O(1). Без union by size (всегда подвешивать меньшее дерево к большему) высота не гарантирована; с ним — логарифмическая; со сжатием путей — почти константная. Скиена: «должен знать каждый программист».
- **Нет:** связи нужно удалять (DSU не разъединяет) → пересчёт обходом (BFS/DFS) или динамические структуры; группы один раз на готовом графе → один обход; нужен сам путь → BFS.
- **Пример:** антифрод — кластеры аккаунтов с общими устройствами.
- **Книга:** 8.1.3, 15.5.

## 3. Сортировка и поиск

В проде — встроенная сортировка языка (отлажена, обычно гибрид). Отдельные алгоритмы нужны, чтобы понять, когда она не подходит: не влезает в память, нужна устойчивость, n мал и почти упорядочено. Устойчивость: при сортировке по дате, затем устойчиво по клиенту заказы клиента остаются по дате. Ориентир: 10⁶ чисел — доли секунды хорошими; простыми (выбор/вставки) — часы, но на 50–100 они не хуже.

**Вопросы перед выбором сортировки (17.1):**
- **Сколько ключей:** ≤ 100 — любой квадратичный (вставки лучше пузырька; сортировка Шелла быстрее обоих и почти так же проста); > 100 — O(n log n); > ~10⁸ — внешняя сортировка.
- **Есть ли дубликаты и важен ли их порядок:** устойчивость проще всего гарантировать, добавив исходную позицию вторичным ключом, а не полагаться на свойства алгоритма.
- **Что известно о данных:** почти упорядочены → вставки; ключи длинные (строки) → сначала по префиксу из ~10 символов, затем досортировать равные, либо radix; ключей из узкого диапазона без повторов (n/2 разных из 1..n) → битовый вектор, O(n).
- **Медленный диск:** загрузить в B-дерево и обойти по порядку, либо k-путевое слияние отсортированных в памяти кусков (через кучу).
- **Насколько важна скорость:** настройка quicksort — случайный/медиана из 3 опорный, вставки для подмассивов ≤ ~20, рекурсия сначала в меньшую часть (стек O(lg n)). Плохо написанный quicksort медленнее плохо написанной пирамидальной сортировки — без нужды не переписывай библиотечную.
- **Приложения сортировки (4.1), которые стоит узнавать:** поиск, ближайшая пара в 1D, уникальность элементов, частота/мода, медиана и выбор, выпуклая оболочка (сортировка по x — первый шаг). Нижняя граница проверки уникальности — Ω(n log n) сравнений, хеш даёт ожидаемое O(n).

### Selection Sort
- **Да:** n≲50 и нужен простейший код; перестановки дороги, сравнения дёшевы (ровно n−1 обменов); основа heapsort (учебно).
- **Нет:** n > нескольких сотен (10⁵ → миллиарды сравнений) → встроенная; почти отсортированные (не замечает) → insertion.
- **Книга:** 2.5.1, 4.3.

### Insertion Sort
- **Да:** n≲100; почти отсортировано; данные по одному, нужен маленький упорядоченный список; финальный проход quick/merge на кусках ≤~20 (Скиена рекомендует).
- **Нет:** тысячи+ вперемешку (10⁵ → минуты) → встроенная; нет гарантии «почти упорядочено» → встроенная.
- **Пример:** таблица лидеров на 20 игроков.
- **Книга:** 2.5.2, 4.3.5, 17.1.

### Heapsort
- **Да:** жёсткая гарантия O(n log n) (real-time) и in-place; нужны только первые K (топ-100 из 10⁶, не сортируя всех).
- **Нет:** нужна устойчивость → merge; нужна макс. средняя скорость — quicksort обычно быстрее (4.6.3) → встроенная (часто introsort с откатом на heapsort).
- **Книга:** 4.3, 17.1.

### Merge Sort
- **Да:** устойчивость; данные не влезают в память (внешняя сортировка — стандарт); связные списки (не нужен random access); гарантия на любых данных и параллелизм (половины независимы).
- **Нет:** память жёстко ограничена, массив огромный (нужен буфер размера n) → heapsort; массив в памяти, устойчивость не нужна → quicksort/встроенная.
- **Пример:** 100 ГБ логов при 16 ГБ RAM; сначала по дате, затем устойчиво по менеджеру.
- **Книга:** 4.5, 17.1.

### Quicksort (рандомизированная)
- **Да:** массив в памяти, нужна макс. практическая скорость; любые данные, в т. ч. отсортированные (случайный pivot исключает плохой случай, 4.6.2); медиана / K-й элемент без полной сортировки (quickselect, 17.3).
- **Нет:** pivot = первый/последний на возможно отсортированных данных → часы на 10⁶; нужна устойчивость → merge; нужна железная гарантия/adversarial → heapsort или introsort; очень много одинаковых значений (5 статусов на 10⁶) → 3-way partition (пр.) или подсчёт.
- **Книга:** 4.6, 17.1, 17.3.

### Bucket Sort / сортировка распределением
- **Да:** значения в известном диапазоне и равномерны (проценты, равномерные ID); ключи — малые целые или короткие строки фикс. формата (возраст, оценки, коды, даты) → counting/radix; объём огромный.
- **Нет:** неравномерно (на «С» и «К» фамилий много, на «Ъ» нет — пример Скиены, 4.7) → встроенная; сложный компаратор (несколько полей, «похожесть») → встроенная с компаратором.
- **Пример:** 10⁷ анкет по возрасту 0–120 — 121 корзина, один проход.
- **Книга:** 4.7, 17.1.

### Binary Search и односторонний двоичный поиск
10⁶ → ~20 шагов, 10⁹ → ~30. Односторонний: пробы 1, 2, 4, 8, … пока не перескочил, затем обычный — когда конец неизвестен или искомое близко к началу.
- **Да:** отсортировано, много поисков; границы (lower/upper bound, «сколько между 10 и 20 марта»); монотонный предикат «нет…нет, да…да» (git bisect, мин. размер партии в бюджет, при какой нагрузке падает сервер); неизвестный размер/поток → односторонний.
- **Нет:** не отсортировано и поиск один раз (сортировка дороже прохода) → линейный проход; данные постоянно меняются → хеш/сбалансированное дерево; предикат не монотонен → перебор.
- **Пример:** git bisect: 1000 коммитов → 10 проверок.
- **Подробности (17.2):**
  - до ~20 элементов последовательный поиск быстрее бинарного, от ~100 — бинарный; при неравномерных частотах (Ципф) последовательный по списку, где частые ключи впереди, может обогнать бинарный;
  - бинарный поиск трудно написать правильно: от первой публикации до первой корректной версии прошло 17 лет. Тест — поиск **каждого** ключа массива и каждого значения **между** соседними ключами;
  - односторонний поиск находит позицию l за ≤ 2⌈lg l⌉ сравнений — выгоден, когда цель близко к текущему месту;
  - интерполяционный поиск (как по словарю — «на букву Ш открываем ближе к концу») Скиена не рекомендует: выигрыш мал, ломается при неравномерных ключах и смене кодировки/локали;
  - внешние данные → B-дерево; частоты меняются → move-to-front/splay; частоты статичны и известны → оптимальное BST (DP).
- **Книга:** 5.1, 5.1.2, 5.1.3, 17.2.

### Медиана и K-й элемент (выбор)
- **Да:** K-й элемент один раз → quickselect, ожидаемое O(n) (линейный в худшем случае алгоритм на практике не нужен); многократные запросы разных K → один раз отсортировать; поток, где все данные не сохранить → случайная выборка с медианой выборки, либо буфер «децилей» с пересчётом; срезать выбросы (оставить 10–90-й процентили), отобрать верхние 25 % кандидатов.
- **Нет:** сортировать ради одной медианы на 10⁸ элементов → quickselect; мода (самое частое значение) через выбор → сортировка + проход или хеш-счётчики.
- **Книга:** 4.6, 17.3.

### Best-First Search
- **Да:** много вариантов, у частичного решения есть оценка «перспективности»; нужно быстро получить хорошее решение; памяти хватит хранить «ждущие» (до миллионов).
- **Нет:** нет хорошей оценки (выродится в BFS с накладными) → BFS/backtracking; вариантов астрономически много — очередь съест память → backtracking+pruning (хранит только ветку) или эвристики гл. 12; задача кратчайшего пути → Дейкстра/A*.
- **Пример:** «пятнашки» — сначала ходы с меньшим числом фишек не на месте.
- **Книга:** 9.6.

### A*
- **Да:** путь A→B (одна цель); есть допустимая эвристика (никогда не завышает: прямая на карте, клетки до цели) — тогда путь кратчайший; граф огромный (карта страны/игры).
- **Нет:** эвристики нет/всегда 0 → Дейкстра; эвристика завышает → путь не кратчайший, исправь или Дейкстра; нужны расстояния до всех или между всеми → Дейкстра/Флойд.
- **Пример:** навигатор курьера; путь робота по сетке склада.
- **Книга:** 9.7.

## 4. Алгоритмы на графах и сетях

Совет Скиена (8.7): «разрабатывай не алгоритмы, а графы» — смоделируй задачу (вершины, рёбра, веса) и бери стандартный алгоритм.

### Обход в ширину (BFS)
- **Да:** кратчайший путь по числу шагов (все шаги равны: рукопожатия, пересадки); достижимое и уровни; двудольность, компоненты; граф в памяти.
- **Нет:** разные веса → Дейкстра; циклы/порядок задач/точки уязвимости → DFS; пространство состояний огромно (волна не влезает) → DFS, A*, backtracking.
- **Книга:** 7.5–7.7.

### Обход в глубину (DFS)
- **Да:** циклы; топосорт; шарниры/мосты; SCC; backtracking = DFS по дереву вариантов.
- **Нет:** нужен кратчайший путь (найдёт петляющий) → BFS/Дейкстра; очень глубокий граф с рекурсией (стек переполнится) → итеративный DFS с явным стеком (пр.).
- **Пример:** циклические зависимости микросервисов; битые ссылки сайта.
- **Книга:** 7.8–7.10.

### Случайный обход графа
- **Да:** граф огромный/не хранится целиком (интернет, соцсеть по API) — нужна выборка или оценка свойств; памяти почти нет (хранится одна вершина); оценка «важности» вершин (идея PageRank, пр.).
- **Нет:** нужно гарантированно посетить всё (время покрытия может быть ≫ обычного обхода) → BFS/DFS; нужен конкретный/кратчайший путь; нужна воспроизводимость → фиксируй seed.
- **Пример:** средний возраст пользователей соцсети через API без скачивания 10⁹ профилей.
- **Книга:** 6.1 («Остановка для размышлений»), 6.2.

### Компоненты связности
- **Да:** связи двусторонние, набор собран целиком (дружба, совпадение телефонов, общая улица) → один BFS/DFS за секунды на миллионах; проверка «всё ли связано».
- **Нет:** связи односторонние (подписки, зависимости) → SCC; связи поступают по одной в реальном времени → DSU; важна надёжность связности → шарниры/связность через потоки.
- **Пример:** склейка дублей клиентов: граф «совпал телефон/email».
- **Подробности (18.1):**
  - проверяй связность входного графа **всегда**, даже если «точно связный» — это дёшево и вскрывает скрытые ошибки в данных и алгоритмах;
  - дерево = связный граф с ровно n − 1 рёбрами (быстрая проверка структуры);
  - слабая связность орграфа (без учёта направлений) vs сильная (односторонние улицы: «можно ли проехать из любого места в любое»).
- **Книга:** 7.7.1, 18.1.

### Сильно связные компоненты (SCC)
- **Да:** орграф: замкнутые круги, «клубки» зависимостей (циклические импорты); схлопнуть SCC → DAG, затем упорядочить; кто взаимно достижим (страницы по кругу, счета с круговыми переводами).
- **Нет:** связи двусторонние → обычные компоненты; минимум связей для удаления всех циклов — трудная задача (19.11) → эвристики, перебор на малых n.
- **Проверка сильной связности без SCC (18.1):** DFS из любой v в G и в транспонированном G; обе обходят все вершины → граф сильно связный. Сами SCC — Косарайю (два DFS) или Тарьян (один), линейно.
- **Разрывающее множество (feedback set, 19.11):** пример Скиены — ранжирование игроков по результатам матчей (циклы «A > B > C > A»). Простая эвристика: упорядочить вершины любым порядком и оставить ту половину дуг (вперёд или назад), которой больше → сохраняется ≥ половины дуг; лучше порядок по разности «выигрыши − проигрыши». Неориентированный граф: минимум удаляемых рёбер = |E| − (n − c), где c — число компонент (остаётся остовный лес); вершинная версия — NP-трудна.
- **Книга:** 7.10.2, 18.1, 19.11.

### Топологическая сортировка
- **Да:** зависимости «A до B», циклов нет: сборка, миграции БД, ETL, пререквизиты; критический путь (самый длинный путь по порядку, 18.2); что можно параллелить (один «уровень»).
- **Нет:** есть цикл (порядка нет) → найти цикл/SCC и разорвать; нужны ещё ресурсы/сроки/ограниченные исполнители → это scheduling (17.9): ILP/эвристики.
- **Подробности (18.2):** два линейных способа — снимать вершины без входящих рёбер через очередь (Кан) или обратный порядок завершения DFS. Перечислить все допустимые порядки — экспоненциально, посчитать их число — трудно; случайный порядок — случайными обменами соседних несравнимых элементов. Если цикл всё-таки есть, DFS-эвристика удаляет ребро, на котором «застряла», и продолжает.
- **Книга:** 7.10.1, 18.2.

### Поиск циклов
- **Да:** валидация ацикличности зависимостей; взаимные блокировки (A ждёт B, B ждёт A); проверка, что структура — дерево (оргструктура, категории).
- **Нет:** самый длинный цикл/через все вершины — трудно (19.5); обход всех рёбер → эйлеров цикл (быстро, 18.7); минимум удалений для разрыва циклов — трудно (19.11) → эвристики.
- **Признак:** в DFS обратное ребро (к предку в дереве обхода) = цикл; в неориентированном графе без обратных рёбер — лес. Взаимная блокировка процессов = цикл в графе ожидания (18.1).
- **Обхват (girth)** — длина кратчайшего цикла: BFS из каждой вершины, O(n·m) (18.4).
- **Книга:** 7.9.1, 18.1, 18.4.

### Эйлеров цикл / задача китайского почтальона (смежно)
- **Да:** пройти **каждое ребро** ровно раз (уборка снега, вывоз мусора, проверка всех переходов меню телефонного автоответчика — пример Скиены). Условия: неориентированный граф — связный и все степени чётные (путь — ровно 2 нечётные вершины); орграф — сильно связный и вход = выход у каждой вершины (путь — у одной +1, у другой −1). Построение — алгоритм Хирхольцера, линейно.
- **Почтальон (рёбра можно повторять, минимизировать длину):** найти кратчайшие пути между вершинами нечётной степени, построить на них паросочетание минимального веса, продублировать эти пути → эйлеров граф. Ни одно ребро не проходится больше двух раз.
- **Нет:** нужно посетить каждую **вершину** раз → гамильтонов цикл (NP).
- **Последовательности де Брёйна** (все k-строки ровно по разу) — эйлеров цикл, а не гамильтонов.
- **Книга:** 18.7, 19.5.

### Шарниры графа (точки сочленения)
- **Да:** единые точки отказа сети/логистики; «выдержит ли сеть отказ любого одного узла»; один обход DFS, секунды на миллионах узлов; аналогично мосты.
- **Нет:** устойчивость к отказу ≥2 узлов/каналов → связность через потоки (18.8); важна достижимость по направлению → SCC + потоки.
- **Подробности (18.8):** вершинная связность ≤ рёберной ≤ минимальной степени вершины (минимальная степень — быстрая верхняя оценка). Рёберная связность графа — n − 1 запусков max-flow от одной вершины до остальных, минимум; вершинная — через расщепление каждой вершины на две, соединённые ребром ёмкости 1 (теорема Менгера: k непересекающихся путей ↔ разрез размера k). Шарнир есть → гамильтонова цикла нет (19.5).
- **Книга:** 7.9.2, 18.8, 19.5.

### Двудольность (2-раскраска)
- **Да:** две группы без конфликтов внутри (две смены/команды/зала); валидация данных («студент—курс» не должен иметь ребро «студент—студент»); перед паросочетанием.
- **Нет:** групп ≥3 (три смены) — раскраска NP-трудна (19.7) → жадные эвристики (по убыванию конфликтов), перебор на малых; «мягкие» конфликты и минимизация их числа → эвристики/ILP.
- **Раскраска при k ≥ 3 (19.7):** пример Скиены — распределение регистров в компиляторе (переменные, живые одновременно, конфликтуют). Ориентиры: любой граф раскрашивается в Δ+1 цветов жадно (Δ — макс. степень); планарный — всегда 4 цвета, простой алгоритм даёт 6, проверка 3-раскрашиваемости NP-полна. Эвристики: жадно по убыванию степени; DSATUR Брелаза (следующей красить вершину с наибольшим числом разных цветов у соседей); улучшение обменом цепей Кемпе (перекраска двухцветной компоненты); отжиг. Рёберная раскраска (расписание пар «преподаватель–группа» без накладок) почти всегда решается Δ или Δ+1 цветами — заметно легче вершинной.
- **Книга:** 7.7.2, 19.7, 19.8.

### Транзитивное замыкание
Транзитивная редукция — минимум рёбер с той же достижимостью (18.5).
- **Да:** запросов «достижимо ли X→Y» очень много, граф меняется редко; вершин тысячи–десятки тысяч (таблица n² в памяти); «развернуть» иерархию (все подчинённые, унаследованные права).
- **Нет:** запросов немного → BFS/DFS на запрос; вершин сотни тысяч+ → обходы по запросу или индексы достижимости (пр.); много циклов → сначала схлопнуть SCC.
- **Пример:** итоговые права роли при наследовании ролей; зависимости ячеек электронной таблицы (что пересчитать при изменении ячейки — пример Скиены).
- **Подробности (18.5):** n обходов BFS/DFS — O(n(n + m)), для разреженных графов вероятно лучший вариант; Уоршелл O(n³) с 1 битом на ячейку; через умножение матриц (возведение в квадрат) — работает, но Штрассен на практике не окупается. Сначала схлопнуть SCC (внутри компоненты все достижимы). Транзитивная редукция: через SCC + DAG легко, если можно добавлять рёбра; минимальная редукция, сохраняющая только исходные рёбра, — NP-полна → эвристика «удаляй ребро (x,y), если есть другой путь x→y».
- **Книга:** 8.3.3, 18.5.

### MST: Прим
- **Да:** плотный граф/матрица расстояний (все пары офисов); строить «от центра».
- **Нет:** соединить только избранные точки (дерево Штейнера, трудно, 8.1.4) → эвристики от остовного; ограничения (степень узла ≤3, глубина) — трудно → эвристики/ILP; разреженный список рёбер → Крускал.
- **Выбор алгоритма MST (18.3):**
  - граф невзвешенный → любое остовное дерево BFS/DFS (DFS — длинное и тонкое, BFS — отражает расстояния от корня);
  - Прим на матрице O(n²) — плотные графы; Крускал O(m log m) — разреженные; Прим с парной кучей — по экспериментам самый быстрый и на разреженных, и на плотных;
  - Борувка — O(m log n) без специальных структур (каждая компонента параллельно берёт своё самое лёгкое внешнее ребро);
  - точки на плоскости → триангуляция Делоне (содержит MST, O(n) рёбер) + Крускал = O(n log n) вместо n² пар;
  - ограничение степени ≤ 2 — это гамильтонов путь (NP); есть приближения, превышающие ограничение на 1.
- **Применения:** кластеризация (удалить самые длинные рёбра), приближения для TSP и дерева Штейнера.
- **Дерево Штейнера (19.10):** MST по терминалам уже хорошее приближение: евклидова метрика — MST не длиннее 1/(√3/2) ≈ 1,155× оптимума; прямоугольная (манхэттенская) — не длиннее 1,5×. Улучшения: точки Штейнера ставить там, где угол между рёбрами < 120° (евклид) / под 90° (прямоугольная); эвристика вставки по кратчайшему пути в графе; удалять листья, не являющиеся терминалами. Применения: разводка микросхем, филогенетические деревья.
- **Книга:** 8.1.1, 8.1.4, 18.3, 19.10.

### MST: Крускал
- **Да:** разреженный граф списком рёбер; рёбра уже отсортированы; кластеризация: остановиться, не добавив k−1 самых дорогих рёбер → k кластеров (пр.).
- **Нет:** очень плотный граф (сортировка всех пар — узкое место) → Прим; те же трудные ограничения (Штейнер, степени) → эвристики.
- **Пример:** дорожная сеть между сёлами; зоны доставки кластеризацией магазинов.
- **Книга:** 8.1.2–8.1.3, 18.3.

### Дейкстра
- **Да:** неотрицательные веса (км, минуты, рубли); расстояния от одной точки до многих/всех; граф большой (город с миллионами перекрёстков — секунды; хорошая реализация лишь в несколько раз медленнее обхода).
- **Нет:** отрицательные веса → Беллман–Форд (цикл с отрицательной суммой → пути нет); все рёбра равны → BFS; одна цель + эвристика → A*; все пары в малом плотном → Флойд–Уоршелл.
- **Подробности (18.4):**
  - нужна одна цель t → останавливать Дейкстру, как только t извлечена из очереди;
  - «прибавить константу ко всем весам, чтобы убрать отрицательные» — **неправильно**: пути с большим числом рёбер штрафуются сильнее, кратчайший путь меняется;
  - DAG → топосорт + релаксация по порядку, линейно и с отрицательными весами; заменив min на max, получаем самый длинный путь (критический путь);
  - путь робота среди препятствий на плоскости → граф видимости (вершины препятствий + старт/финиш, рёбра — прямые без пересечений) + Дейкстра;
  - характеристики графа: эксцентриситет вершины (самый дальний путь), радиус/центр (минимальный эксцентриситет — где ставить склад), диаметр;
  - применения из книги: сегментация изображений (разрез по «дешёвому» пути), распознавание речи (путь по графу вариантов слов).
- **Книга:** 8.3.1, 18.4.

### All-Pairs Shortest Paths
Флойд–Уоршелл: три цикла по матрице.
- **Да:** нужна вся таблица (логистика, «центр» сети, диаметр); n до нескольких тысяч (1000 → ~1 с в компилируемом языке; 10 000 → десятки минут–часы и ~800 МБ); отрицательные веса без отриц. циклов — Флойд ок.
- **Нет:** n сотни тысяч+ → Дейкстра по запросу/дорожные индексы (пр.); большой разреженный → Дейкстра от каждой вершины (быстрее Флойда), при отриц. весах — Джонсон; нужен один источник → Дейкстра.
- **Нюанс (18.4):** Флойд намного проще в коде, чем n запусков Дейкстры, и требует O(n²) памяти — при n ≲ нескольких тысяч простота обычно важнее асимптотики.
- **Книга:** 8.3.2, 18.4.

### Максимальный поток
- **Да:** макс. пропускная способность (трафик, грузы, энергия); распределение с лимитами по количеству (≤3 задачи на человека); число непересекающихся путей, узкое место (min-cut).
- **Нет:** чистое назначение 1:1 → паросочетание (проще и быстрее); есть «всё или ничего», фикс. плата за трубу, несколько товаров с целыми количествами → ILP/LP; писать самому для большой сети → Boost Graph, LEDA, NetworkX.
- **Подробности (18.9):**
  - совет Скиены: сначала запиши задачу как LP, затем сравни с max-flow / min-cost-flow — если совпало, бери специализированный алгоритм (быстрее LP);
  - несколько источников/стоков → суперисточник/суперсток, соединённые с ними рёбрами бесконечной ёмкости;
  - все ёмкости 0/1 (непересекающиеся пути) → есть более быстрые алгоритмы;
  - несколько видов товара (multicommodity): дробные потоки → LP; неделимые — NP-полно даже для двух товаров;
  - push-relabel на практике быстрее увеличивающих путей — он стоит в хороших библиотеках.
- **Книга:** 8.5, 18.9, 22.1.

### Минимальный разрез (произвольный)
Простой рандомизированный способ (Каргер): случайно склеивать вершины, пока не останутся две, повторять, брать лучший.
- **Да:** надёжность сети (сколько связей минимум оборвать); разбить на две слабо связанные части (естественные кластеры); устраивает «с высокой вероятностью верно» при многократном повторе.
- **Нет:** разрез между конкретными двумя точками → max-flow (его величина и есть min-cut); нужна строгая гарантия → детерминированно (через потоки, Стор–Вагнер, пр.); части должны быть примерно равны (balanced partition — трудно, 19.6) → эвристики/библиотеки разбиения графов.
- **Разбиение графа (19.6):** минимальный разрез часто отрезает одну вершину — для «разбить нагрузку на машины» он бесполезен, нужен сбалансированный. Разделители: у дерева всегда есть вершина, после удаления которой компоненты ≤ n/2; у планарного — разделитель из O(√n) вершин. Эвристики: локальное улучшение (перекладывать вершины между частями, пока разрез уменьшается), спектральные методы (собственный вектор лапласиана) + локальная доводка. Максимальный разрез — тоже NP-трудная, решается теми же локальными перекладками.
- **Книга:** 8.6, 18.8, 19.6.

### Паросочетание в двудольном графе
С весами — задача о назначениях (венгерский алгоритм).
- **Да:** «один к одному» (водители↔заказы, кандидаты↔вакансии); максимум пар или лучшее суммарное качество; размер до сотен тысяч узлов — секунды.
- **Нет:** пары внутри одной группы (соседи по комнате) → алгоритм Эдмондса (общий граф), лучше из библиотеки; «никто не захочет поменяться» (предпочтения) → устойчивые пары Гейла–Шепли (пр.); один элемент берёт несколько пар → поток.
- **Пример:** такси — минимум суммарного времени подачи.
- **Подробности (18.6):** работник может взять k задач → продублировать его вершину k раз; основа всех алгоритмов — увеличивающие пути (теорема Бержа: паросочетание максимально ⇔ увеличивающего пути нет); с весами — венгерский алгоритм. Пример Скиены: переставить буквы строки так, чтобы ни одна не осталась на своём месте (aaabc → bcaaa) — двудольный граф «позиция — буква».
- **Книга:** 8.5.1, 18.6.

## 5. Строковые и математические алгоритмы

### Поиск подстроки (точное совпадение)
- **Да:** обычный поиск → встроенный find/indexOf/in (2.5.3, 21.3); длинный образец (>~10 символов), редко встречается → Бойер–Мур; гарантия на любых данных → КМП; много образцов (10 000 запрещённых слов) → Ахо–Корасик или Карп–Рабин (6.7); множество запросов по одному огромному тексту (геном, архив) → суффиксный массив/дерево заранее (15.3).
- **Нет:** опечатки/похожие → edit distance/fuzzy (10.2, 21.4); шаблон (телефон, email) → regex; патологические повторы («аааа…аб») при самописном поиске в лоб — тысячекратный провал → КМП/встроенный; полнотекстовый поиск по миллионам документов с формами слов → поисковый движок (Elasticsearch, пр.).
- **Пример:** grep ID запроса в логах; модерация чата по 5000 слов за проход (Ахо–Корасик).
- **Подробности (21.3):**
  - образец ≤ ~10 символов → наивный поиск обычно практически линеен; его худший случай — образец aaa…ab в тексте aaa…a;
  - Бойер–Мур сравнивает с конца образца и прыгает далеко — на длинных образцах и больших алфавитах лучший; худший случай O(n + rm), где r — число вхождений;
  - много образцов одновременно — Ахо–Корасик (так работает `fgrep`);
  - регулярное выражение → конечный автомат (недетерминированный → детерминированный); образцы со структурой «грамматики» → парсер.
- **Книга:** 2.5.3, 6.7, 15.3, 21.3.

### Расстояние редактирования (Левенштейн)
Минимум вставок/удалений/замен; DP по таблице.
- **Да:** опечатки, «вы имели в виду», сверка ФИО/адресов; diff версий (таблица даёт сами правки, 10.2.3); строки короткие–средние (до тысяч символов); вариации (цены правок, поиск с ошибками внутри текста, наибольшая общая подпоследовательность, 10.2.4).
- **Нет:** строки ≥10⁵ символов (таблица не влезает) → две последних строки таблицы; для самих правок — Хиршберг; для почти одинаковых — быстрые специальные версии; «каждый с каждым» на 10⁶ записей = 10¹² → сначала кандидаты (первые буквы, фонетический код, общие куски слов), расстояние внутри групп; сходство по набору слов («Иван Петров»/«Петров Иван») → MinHash/множества; сходство «на слух» → Soundex (21.4).
- **Пример:** дедупликация «ООО Ромашка» vs «ООО «Ромашка»»; «телевезор» → «телевизор»; оценка качества OCR — сравнение распознанного текста с эталоном (пример Скиены).
- **Варианты DP (21.4):**
  - поиск образца с ошибками **внутри** текста: первая строка таблицы D[0, j] = 0 (начинать можно где угодно), ответ — минимум по последней строке;
  - цены операций настраиваемы; если замена дороже вставки + удаления, задача превращается в наибольшую общую подпоследовательность (LCS);
  - строки почти одинаковы (расстояние ≤ d) → считать только полосу шириной O(d) вокруг диагонали, O(dn);
  - короткий образец (≤ размера машинного слова) → битово-параллельный алгоритм (как в `agrep`), очень быстро;
  - длинные строки, но нужны сами правки → Хиршберг: линейная память ценой ~2× времени;
  - пропуски в выравнивании (ДНК, тексты) → аффинный штраф A + B·t за пропуск длины t (один длинный пропуск дешевле многих коротких);
  - Soundex: первая буква + 3 цифры по группам согласных («Skiena» → S25) — грубо, но ловит фамилии «на слух».
- **Книга:** 10.2, 21.4.

### Синтаксический разбор (Parsing)
Универсальный разбор через DP (10.8) — CYK-подобный; время растёт быстро с длиной.
- **Да:** произвольная/неоднозначная грамматика, короткие строки (формулы, команды, предложения); расстановка скобок/разбиение последовательности по правилам; прототип, скорость не критична.
- **Нет:** языки программирования, JSON/XML/CSV/SQL, длинные файлы → готовые парсеры/генераторы (ANTLR, yacc; стандартные библиотеки), один проход (пр.); простые шаблоны (даты, телефоны, коды) → regex; свой парсер JSON/CSV «на коленке» — не надо.
- **Пример:** формулы в конструкторе отчётов (ок). 100-МБ XML универсальным методом (плохо → потоковый парсер).
- **Книга:** 10.8.

### Быстрое умножение и быстрое возведение в степень
Степень: квадраты вместо 1000 умножений (~20 шагов, 2.7.5); большие числа — Карацуба (5.5), далее FFT.
- **Да:** большие степени, особенно по модулю (крипто, хеши, простота); далёкий член рекуррентности (Фибоначчи №10⁹) возведением матрицы в степень; числа огромные (тысячи+ цифр).
- **Нет:** числа в 64 бита → встроенная арифметика; писать длинную арифметику самому → GMP/BigInteger/Python int (16.9); нужны вещественные степени → pow с учётом погрешности.
- **Пример:** RSA: огромное число в огромную степень по модулю за доли мс.
- **Подробности (16.9):**
  - разовый расчёт → Python или система компьютерной алгебры (Mathematica, Maple); встраиваемое приложение → библиотека (GMP, BigInteger);
  - своя реализация: основание системы ≈ √(максимальное целое машины), чтобы произведение «цифр» не переполнялось;
  - по Скиене Карацуба выгоднее школьного умножения уже на числах **заметно меньше 100 цифр**; на очень больших — FFT; библиотека переключает методы сама;
  - деление — повторными вычитаниями со сдвигом (как столбиком); возведение в степень — делением показателя пополам;
  - высокая, но не произвольная точность и нет деления → китайская теорема об остатках: считать по нескольким простым модулям и восстанавливать;
  - многочлен вычислять по схеме Горнера (n умножений вместо ~n²/2).
- **Книга:** 2.7.5, 5.5, 5.9, 16.9.

### Свёртка (Convolution) и быстрое полиномиальное умножение
Скользящее взвешенное суммирование; БПФ делает быстро.
- **Да:** сигналы, звук, изображения (фильтры, корреляция, поиск фрагмента); перемножение очень длинных многочленов/чисел; оба ряда длинные (10⁶ точек: БПФ — доли секунды вместо часов); образец с джокерами в длинной строке (5.9.1).
- **Нет:** один ряд короткий (окно 3–10, скользящее среднее) → прямой подсчёт; нужна точность целых (БПФ на float даёт ошибки округления) → NTT или округление с проверкой (пр.); писать БПФ самому → FFTW (рекомендует Скиена, 16.11), numpy.fft, scipy.signal.
- **Применения ДПФ (16.11):** фильтрация (убрать высокие частоты = шум, обратное преобразование); сжатие (отбросить малые коэффициенты); деконволюция (убрать известное искажение); корреляция — пример Скиены: проверка генератора случайных чисел на периодичность (пик в спектре = период). Длину дополнять нулями до степени 2.
- **Книга:** 5.9, 16.11.

### Тестирование чисел на простоту
Миллер–Рабин: «составное» — точно; «простое» — с вероятностью, повторами доводится до уверенности (20–50 повторов; ошибка ниже сбоя железа). Обходит числа Кармайкла (ловушка для теста Ферма).
- **Да:** числа огромные (крипто-ключи, сотни цифр) — миллисекунды; нужна практическая уверенность.
- **Нет:** числа маленькие (до ~10⁹) → пробное деление до √n; нужны все простые до N (10⁷) → решето Эратосфена (пр.); нужна **факторизация** (тест простоты её не делает, она гораздо труднее — на этом держится RSA, 16.8); простой тест Ферма там, где важна надёжность → Миллер–Рабин.
- **Пример:** генерация RSA-ключа — случайные 300-значные числа + Миллер–Рабин; размер хеш-таблицы простым числом — проверка делением.
- **Подробности (16.8):**
  - пробное деление экспоненциально по **числу битов** (√n = 2^(b/2)) — для сотен цифр безнадёжно;
  - плотность простых ≈ 1/ln n → чтобы найти следующее простое после n, нужно проверить порядка ln n чисел (для 300 цифр — сотни, отсюда «PGP находит простое за минуты»);
  - много проверок небольших чисел → заранее битовая таблица простых (нечётные до 10⁶ — меньше 64 КБ);
  - факторизация: рекорд решетом числового поля — числа порядка 250 цифр; квантовый алгоритм Шора для RSA-2048 по оценкам требует ~20 млн кубитов (на сегодня нереально).
- **Книга:** 6.8, 12.6.1, 16.8.

### Биномиальные коэффициенты и числа Фибоначчи
- **Да:** «K из N» — треугольник Паскаля или поочерёдное умножение/деление (без переполнения, 10.1.4); Фибоначчи — цикл с двумя последними значениями (10.1.3); очень далёкий член — быстрое возведение матрицы в степень.
- **Нет:** Фибоначчи рекурсией без кэша (40–50 — минуты, 100 — вечность, 10.1.1) → цикл/кэш; C(n,k) через факториалы «в лоб» (21! не влезает в 64 бита) → Паскаль; C(n,k) mod p для больших n → обратные элементы (пр.).
- **Пример:** комбинации начинок для пиццы из 15 — Паскаль.
- **Книга:** 10.1.

### НОК
Через НОД: алгоритм Евклида (десятки шагов даже для чисел из сотен цифр); `lcm = a / gcd(a,b) * b`.
- **Да:** когда совпадут периодические процессы (cron 15/20/45 мин → 180 мин); общий знаменатель дробей; любые числа.
- **Нет:** через разложение на простые (для больших — трудно, 16.8) → через НОД; перебор кратных (4, 8, 12…) → через НОД; сначала a·b, потом деление на gcd (переполнение) → сначала a/gcd, потом умножать (пр.).
- **Книга:** 11.2.3.

## 6. Классические комбинаторные и NP-полные задачи

Порядок для NP-трудных (гл. 11–12): малые данные (≲15–30) — перебор с отсечениями; средние — ILP/SAT-солверы; большие — эвристики: быстро построить, затем улучшать (локальный поиск, имитация отжига — по Скиене самый надёжный практический вариант, 12.6).

### TSP / маршрут робота
- **Да:** n≲10–12 → полный перебор (точно); десятки–сотни точек → вставки («вставить точку туда, где маршрут удлиняется меньше») + 2-opt/локальный поиск/отжиг (12.6, 19.4), обычно в пределах нескольких % от идеала; точки на плоскости → Кристофидес (гарантия ≤1,5–2× от оптимума, 12.3); максимум качества, тысячи точек → Concorde (лучшая по Скиене, 19.4), OR-Tools (пр.); n≲20 в DP по подмножествам (Хелд–Карп).
- **Нет:** окончательный маршрут правилом «в ближайшую» (очень плох, 1.1) — только как старт; точный оптимум перебором при 30+ → эвристики/Concorde; нужно пройти **по всем улицам** (почтальон, снег) → задача китайского почтальона (лёгкая, 18.7).
- **Пример:** курьер, 40 заказов: вставки + 2-opt за доли секунды; экономия 20–40 % к порядку «как пришли»; робот, паяющий контакты на плате (пример Скиены).
- **Вопросы перед выбором (19.4):**
  - выполняется ли неравенство треугольника (без него эвристики с гарантией не работают; авиатарифы его нарушают — прямой рейс бывает дороже рейса с пересадкой);
  - точки на плоскости или граф: для точек расстояния считать по требованию, не хранить n² матрицу;
  - можно ли посещать вершины повторно → заменить веса кратчайшими путями (APSP), и тогда неравенство треугольника выполняется;
  - асимметричные расстояния (односторонние улицы, ветер) → сведение к симметричной задаче на 2n вершинах;
  - невзвешенный граф → это гамильтонов цикл.
- **Качество эвристик по Скиене (19.4):** обход MST — обычно на 15–20 % хуже оптимума (гарантия ≤ 2×); вставка самой дальней точки — 5–10 %; 2-opt / 3-opt — несколько %, 3-opt заметно лучше 2-opt, k > 3 почти не даёт выигрыша. Точно — метод ветвей и границ / секущие плоскости (Concorde решает тысячи вершин).
- **Эксперимент 12.6 (150 городов):** 10⁸ случайных маршрутов — в 8 раз хуже оптимума; hill climbing — в 2,3 раза; имитация отжига — близко к оптимуму. Вывод: случайная выборка для TSP бесполезна, локальный поиск без отжига слаб.
- **Книга:** 1.1, 12.3, 12.6, 19.4.

### Календарное планирование (Scheduling)
- **Да:** один ресурс, максимум непересекающихся интервалов → сортировка по раннему окончанию, жадно (доказуемо оптимально, 1.2); зависимости и минимальное время проекта → топосорт + критический путь (18.2); назначение исполнителей 1:1 → паросочетание/поток (18.6, 18.9); много сотрудников/смен/правил → ILP/CP-SAT/специализированный солвер (16.6, 17.9).
- **Нет:** интервалы по «самой короткой» или «самой ранней по началу» (контрпримеры Скиены, 1.2); интервалы с разной ценностью (веса) → DP (пр.); несколько станков с переналадками и общими ресурсами — трудно → CP-SAT/ILP/эвристики (17.9).
- **Пример:** одна переговорка, 30 заявок — по окончанию; график 25 медсестёр на месяц — модель для солвера.
- **Сведение к известным задачам (17.9):** порядок с зависимостями → топосорт; назначение работ работникам → паросочетание; расписание без накладок по ресурсам → вершинная/рёберная раскраска; минимизация переналадок между работами → TSP; обход всех переходов → эйлеров цикл.
- **Подробности (17.9):**
  - критический путь = самый длинный путь в DAG работ, O(n + m); минимальное время проекта при неограниченных исполнителях — по уровням топосорта;
  - фиксированное число исполнителей + зависимости → NP-полно, эвристики;
  - k одинаковых машин, работы без зависимостей, минимизировать время → это bin packing;
  - задача становится лёгкой, если работы можно делить/прерывать (preemption); трудность — именно от неделимости;
  - неявные/«мягкие» ограничения: сначала игнорировать и потом исправлять решение вручную, либо сразу ILP. Скиена: начни с простого.
- **Книга:** 1.2, 17.9.

### Максимальный поддиапазон (Maximum Subarray)
В книге — D&C (5.6); проще — Кадане за один проход (пр.).
- **Да:** «лучший период» (самая прибыльная серия дней, участок графика/сигнала); в ряду есть отрицательные; данных миллионы.
- **Нет:** перебор всех пар «начало–конец» (10⁶ → 10¹²) → один проход; все числа ≥0 (ответ — весь ряд); доп. условия (длина 7–30, 2D) → модифицированные версии на префиксных суммах (пр.).
- **Пример:** лог: вычесть норму, найти отрезок с макс. суммой превышения.
- **Книга:** 5.6.

### Ближайшая пара точек / выпуклая оболочка
- **Да:** 1D (цены, даты) — отсортировать, сравнить соседей (11.2.1); точки на плоскости, тысячи–миллионы → D&C для ближайшей пары (5.6); многократные запросы «ближайший к этой» → kd-дерево (15.6, 20.5); контур точек → Грэхем (сортировка + обход, 11.2.4, 20.2), «заворачивание подарка» если вершин оболочки заведомо мало; в проде — CGAL, Shapely, scipy.spatial.
- **Нет:** «каждая с каждой» на десятках тысяч+ → сортировка/индекс; измерений десятки–сотни (эмбеддинги) → kd-деревья и оболочки бесполезны → приближённый поиск соседей (FAISS, Annoy, пр.); самописная геометрия на float без учёта вырожденных случаев (коллинеарность, совпадающие точки, 20.1) → готовая библиотека.
- **Пример:** две ближайшие метеостанции — слить дубли датчиков; зона обслуживания курьеров по адресам за месяц (оболочка).
- **Ближайший сосед (20.5):** примеры Скиены — ближайшая пожарная часть к адресу, классификатор «по ближайшему соседу», сжатие векторным квантованием в 64-мерном пространстве. n ≤ ~100 или запросов мало → линейный просмотр; 2D статично → диаграмма Вороного; 2–20 измерений → kd-дерево; около 20+ измерений kd-дерево вырождается в перебор → шаровые деревья, случайные проекции в пространство меньшей размерности, приближённый поиск (случайно возмущённые запросы). Обновления редки → периодически перестраивать структуру.
- **Выпуклая оболочка (20.2):** до построения отбросить точки внутри четырёхугольника из крайних точек (min/max по x и y) — часто большинство. Грэхем O(n log n) по умолчанию; «заворачивание подарка» O(nh) — когда вершин оболочки h мало. Диаметр множества — по оболочке методом вращающихся калиперов. Нужна невыпуклая форма облака точек → alpha-shapes.
- **Геометрические примитивы (20.1):** вырожденные случаи (коллинеарные, совпадающие точки) — игнорировать, случайно возмутить координаты или обрабатывать явно; лучшее числовое представление — целочисленная сетка; хранить float, считать в double. Базовые операции через определители: знаковая площадь треугольника (ориентация «левый/правый поворот», пересечение отрезков), тест «точка внутри окружности».
- **Пересечения (20.8):** проверить «есть ли пересечение» проще, чем построить его; n отрезков → заметающая прямая, O(n log n + k) для k пересечений; два выпуклых многоугольника → O(n + m); движущиеся объекты → сначала ограничивающие прямоугольники (дешёвый отсев), точная проверка только для пересёкшихся.
- **Книга:** 5.6, 11.2.1, 11.2.4, 15.6, 20.1, 20.2, 20.5, 20.8.

### Пересечение множеств и дубликаты
- **Да:** обычно → set/хеш (одну в set, вторую проверить; 3.7.2, 4.1); нужен порядок/данные отсортированы/не влезают в память → сортировка обеих + одновременный проход; один список мал, второй огромен → отсортировать малый, искать бинарным поиском; миллиарды и допустима редкая ошибка → Bloom (6.4); почти-дубли → MinHash (6.6).
- **Нет:** два вложенных цикла на тысячах+ (2×10⁵ → 10¹⁰); сравнение «как есть», когда дубли отличаются регистром/пробелами/форматом → сначала каноникализация (3.7.4); нечёткие дубли (опечатки ФИО) → edit distance + группировка кандидатов.
- **Пример:** сверка оплат банка и заказов CRM — два set и разность.
- **Ориентир:** проверка уникальности сравнениями не быстрее Ω(n log n) — сортировка + проход оптимальна среди методов сравнения; хеш даёт ожидаемое O(n) (17.3). Мода/частоты — тем же способом.
- **Книга:** 3.7.2, 3.7.4, 4.1, 15.5, 17.3.

### Генерация всех подмножеств, перестановок и путей
- **Да:** подмножества n≲20–25, перестановки n≲10–12, пути только в малых графах; эталон/точный ответ на маленьком примере; тестовые данные «все комбинации» (8 галочек = 256); случайная перестановка → Фишер–Йетс (17.4).
- **Нет:** n=30 → 10⁹ подмножеств, n=15 → >10¹² перестановок, путей в графе — астрономически → перебор с отсечениями, DP, солверы, эвристики; shuffle сортировкой по случайному ключу или самодельным способом (некоторые порядки чаще, частая ошибка, 17.4) → Фишер–Йетс/stdlib shuffle; нужен один кратчайший путь → Дейкстра/BFS.
- **Подробности (17.4):**
  - лексикографический порядок часто не нужен — подойдёт любой, который проще генерировать;
  - rank/unrank (перестановка ↔ номер): следующая/предыдущая перестановка, случайная (unrank случайного числа), учёт «уже видели» битовым вектором по номеру; работает, пока n! влезает в целое (≈ n ≤ 20 для 64 бит);
  - генерация с минимальными изменениями (соседние перестановки отличаются одним обменом) — дешёвый инкрементный пересчёт стоимости;
  - Фишер–Йетс правильно: `for i in 1..n: swap(a[i], a[Random(i, n)])`; ошибка: `Random(1, n)` — даёт неравномерное распределение (nⁿ исходов не делится на n!).
- **Книга:** 9.2, 17.4–17.5.

### Самая длинная возрастающая подпоследовательность (LIS)
Не обязательно подряд, порядок исходный; в 5,2,8,3,9,4,10 это 2,3,4,10.
- **Да:** «устойчивый рост» с игнорированием выбросов; согласованность двух порядков; минимум перестановок, чтобы упорядочить (всё вне LIS переставить); O(n²) DP хватит на тысячи, ускоренный вариант с бинарным поиском — на миллионы (11.2.2; детали — пр.).
- **Нет:** нужен непрерывный отрезок роста → простой цикл; перебор всех подпоследовательностей (40 → 10¹²) → DP; сравнение двух разных рядов/строк → наибольшая общая подпоследовательность/edit distance.
- **Пример:** плейлист на 500 треков, сколько «перетащили» — всё вне LIS.
- **Книга:** 10.3, 11.2.2.

### Сумма подмножества (неупорядоченное разбиение) и упорядоченное разбиение
Subset sum: набрать ровно сумму / поделить на равные части; родственник — рюкзак (16.10). Упорядоченное: порядок менять нельзя, разрезать на K кусков, минимизируя самый тяжёлый (главы между переводчиками).
- **Да:** subset sum: целые числа, суммы до миллионов → DP по таблице; n≲20–40 при любых числах → перебор/«встреча посередине» (пр.); упорядоченное: поровну разнести последовательную работу (главы, диапазоны записей) → DP на тысячах элементов (10.7) или бинарный поиск по ответу (пр.).
- **Нет:** числа огромные (суммы в миллиарды копеек) и n много → округление/приближения, солверы, эвристики (16.10); жадное «сначала крупные» для точной суммы → DP; порядок на самом деле можно менять → это bin packing/балансировка.
- **Пример:** какие из 30 счетов дают ровно 1 247 380 ₽; 10 000 строк по дате на 4 воркера непрерывными кусками.
- **Рюкзак (16.10) — сначала проверь частный случай:**
  - предметы делимы (сыпучие) → жадно по цене за единицу веса — оптимально;
  - у всех предметов одинаковая цена → брать по возрастанию размера; одинаковый размер → по убыванию цены;
  - у всех одинаковая цена за кг → это subset sum (всё ещё NP, но DP проще);
  - DP O(n·C) времени и O(C) памяти: отлично для ёмкости C ≲ 10³–10⁶, бесполезно для C ≈ 10⁹;
  - большие C → масштабирование: поделить размеры на C/C_s, округлить, решить DP для ёмкости C_s (приближённо);
  - несколько рюкзаков → bin packing.
- **Книга:** 10.5, 10.7, 16.10.

### Bin Packing
- **Да:** все предметы известны заранее → сортировка по убыванию + «первый подходящий» (лучший простой метод, 20.9); плоские/объёмные предметы → упрощение до прямоугольников и укладка рядами/полками; точный минимум при нескольких десятках предметов → ILP/перебор с отсечением; при необходимости улучшить локальным поиском.
- **Нет:** укладка в порядке поступления, когда список известен (хуже) → сначала сортировка; оптимум перебором для сотен предметов; онлайн (предметы по одному) — «первый подходящий», но закладывай запас: онлайн всегда хуже (20.9).
- **Пример:** сколько грузовиков по 20 т для 140 заказов; раскрой фанеры; VM по серверам.
- **Подробности (20.9):**
  - «первый подходящий по убыванию» никогда не использует больше ~22 % контейнеров сверх оптимума (11/9·OPT) — для большинства практических задач хватает;
  - важна ориентация: квадрат 3×3 нельзя замостить плитками 2×1 без учёта поворотов (пример Скиены); если поворачивать нельзя — модель другая;
  - ограничения упаковки: «не ставить сверху» — грузить последними, «этой стороной вверх» — первыми;
  - фигуры неправильной формы → вписать в ограничивающие прямоугольники; пустоты внутри невыпуклых фигур использовать для мелких предметов.
- **Книга:** 20.9.

### Гамильтонов цикл
«Коммивояжёр без расстояний»: каждая вершина ровно один раз.
- **Да:** n≲20–30 → backtracking+pruning или DP по подмножествам (19.5); большой граф → свести к TSP (есть связь = 1, нет = 2) и запустить Concorde; спецграфы, где легко (турниры, 19.5).
- **Нет:** нужно пройти каждое **ребро** ровно раз → эйлеров цикл, быстро (18.7); точный перебор на сотнях вершин → TSP-солвер/эвристики; нужен «какой-нибудь цикл»/связность → DFS (7.9.1).
- **Пример:** 18 экспонатов по проходам без повторов — перебор; 200 постов охраны — TSP-солвер.
- **Быстрые проверки до перебора (19.5):** есть шарнир (граф не двусвязен) → цикла нет; все степени ≥ n/2 (теорема Дирака) → цикл точно есть и находится легко; самый длинный путь в DAG — линейно (DP), трудна только версия с циклами. Коды Грея — гамильтонов цикл на гиперкубе (строятся явно). Если удаётся переформулировать «вершины» как «рёбра» (де Брёйн) — получится эйлеров цикл, линейно.
- **Книга:** 11.3.1, 19.5.

### Независимое множество, вершинное покрытие, клика
По сути одна задача в трёх обличьях (11.3.2–11.3.3).
- **Да:** граф ≲50–100 вершин → точно перебором с отсечениями (19.1–19.3); вершинное покрытие с гарантией ≤2× оптимума: взять оба конца непокрытого ребра (12.2); большой граф → жадные эвристики (для покрытия — сначала самые «связанные», для независимого — самые «одинокие») + локальный поиск/отжиг (12.2.1, 12.6); дерево или двудольный граф → быстро и точно (DP, паросочетания, 19.2–19.3).
- **Нет:** точный ответ на графе из тысяч вершин → эвристики/ILP с лимитом времени; макс. клика в огромной соцсети «ради сообществ» (и трудно, и не то) → выделение сообществ, k-ядра (пр., 19.1); не заметили, что граф дерево/двудольный.
- **Пример:** минимум датчиков на узлах трубопровода (2-approx покрытия).
- **Клика (19.1):** пример Скиены — налоговая ищет группы мошеннических деклараций (одинаковые реквизиты = рёбра, группа = клика). Максимальную клику трудно даже приблизить (в n^(1−ε) раз). Практика: жадная максимальная (не максимальная по размеру) клика — вершины по убыванию степени, добавлять, пока смежна со всеми выбранными; повторять со случайными стартами. Плотные подграфы вместо клик → k-ядро (удалять вершины степени < k, O(n + m)). Отсечение в точном переборе: клика размера j возможна только среди вершин степени ≥ j − 1. В планарном графе клика ≤ 4.
- **Независимое множество (19.2):** примеры — размещение объектов, которые не должны стоять рядом (конкурирующие точки франшизы), выбор кодовых слов с большим расстоянием. Равно клике в дополнении графа; самый большой цветовой класс любой раскраски — готовое независимое множество; жадно: брать вершину минимальной степени и удалять её соседей; в дереве — точно за линейное время (брать листья).
- **Вершинное покрытие (19.3):** жадность «вершина максимальной степени» бывает в lg n раз хуже; максимальное паросочетание (оба конца каждого ребра) — гарантия 2×; второй проход удаляет вершины, все рёбра которых покрыты другими. Доминирующее множество (каждая вершина в множестве или рядом) — жадно с гарантией ln n. Рёберное покрытие (покрыть вершины рёбрами) — полиномиально через паросочетание.
- **Книга:** 11.3.2–11.3.3, 11.5.1, 12.2, 19.1–19.3.

### Покрытие множества / hitting set (смежно)
- **Да:** выбрать минимум наборов, покрывающих все элементы (лотерейные билеты, покрывающие все комбинации; минимизация логических схем; минимум сотрудников, покрывающих все навыки). Жадно «набор, покрывающий больше всего непокрытых» — гарантия ≤ ln n, на практике обычно близко к оптимуму; элементы, входящие ровно в один набор, — этот набор брать сразу. Точно → ILP (переменная на набор, ограничение на элемент); LP-релаксация + округление; улучшение отжигом.
- **Частные случаи:** все наборы по 2 элемента → рёберное покрытие, полиномиально через паросочетание; каждый элемент ровно в 2 наборах → вершинное покрытие. Hitting set (выбрать минимум элементов, задевающих каждый набор) — двойственная задача, те же методы.
- **Нет:** точный перебор на сотнях наборов → ILP с лимитом времени.
- **Книга:** 12.5, 21.1.

### SAT и 3-SAT
- **Да:** задача описывается логическими правилами (конфигуратор «мотор X ⇒ нельзя кузов Y», совместимость версий пакетов, жёсткие запреты в расписании, проверка логики); готовый SAT-солвер (MiniSat, CaDiCaL) тянет миллионы условий реальных задач (17.10); **2-SAT** (по 2 переменные в условии) решается быстро и точно через граф (11.4.1); нужно выполнить как можно больше условий → MAX-SAT (случайные значения уже дают в среднем 7/8 условий 3-SAT, затем улучшать, 12.4.1).
- **Нет:** свой солвер «с нуля» → готовые; много чисел и сумм («бюджет ≤100 000», «минимизировать стоимость») → ILP/CP-SAT (пр.); специально сгенерированные случайные трудные формулы → ограничить время, MAX-SAT/эвристики.
- **Пример:** менеджеры пакетов (pip/apt/npm) подбирают версии SAT-подобными солверами (пр.); верификация схем/программ — выполнима ли формула S(X) ≠ C(X) (найдётся вход, где спецификация и реализация расходятся) — пример Скиены.
- **Подробности (17.10):**
  - форма важна: КНФ (И из ИЛИ) — NP-полна; ДНФ (ИЛИ из И) проверяется тривиально, но перевод КНФ → ДНФ экспоненциален;
  - 1-SAT тривиальна, 2-SAT линейна (граф импликаций + SCC), 3-SAT уже NP-полна;
  - точный метод — перебор с возвратом Дэвиса–Патнэма (DPLL) с распространением единичных дизъюнктов; современные солверы — его развитие;
  - случайные экземпляры чаще всего лёгкие: трудны только при определённом соотношении числа дизъюнктов к переменным (≈ 4,26 для 3-SAT, пр.);
  - MAX-SAT: случайное присваивание выполняет в среднем долю 1 − (1/2)^k дизъюнктов длины k; затем улучшать локальным поиском.
- **Книга:** 11.4–11.5, 12.4.1, 17.10.
